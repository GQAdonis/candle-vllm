02 — candle-vllm (feature/god-mode)

The Parking-Lot Scheduler — Core Innovation

The parking-lot scheduler is the most architecturally significant change in the fork. It replaces naive tokio task spawning with a resource-aware OS thread pool that performs true GPU memory accounting before accepting a job.

Resource Accounting

Each request's estimated token count maps directly to KV-cache block units. The scheduler tracks live GPU capacity and queues or rejects work before the GPU sees it — preventing the OOM crashes that plague naive inference deployments.

Backpressure by Design

When GPU capacity is exhausted, excess requests queue to max_queue_depth. Beyond that, clients receive HTTP 503. This is a correct, production-ready contract — not a crash. Every job wraps in catch_unwind for panic safety across worker threads.

Deployment note: The parking-lot scheduler directly enables Prometheus Fabric's multi-agent concurrency model. Multiple agents can issue inference requests simultaneously without coordination overhead — the scheduler handles contention at the resource layer, not the application layer.

03 — turboquant-rs

Pure Rust Implementation of Google Research's ICLR 2026 Algorithm

TurboQuant-RS is the first production-grade Rust implementation of TurboQuant (Google Research, ICLR 2026). It compresses transformer KV-cache vectors to 3 bits per coordinate using a two-stage pipeline of randomised Hadamard rotation and Lloyd-Max scalar quantisation, achieving 6–10× memory reduction with under 2% inner product error and negligible perplexity impact.

Algorithm Architecture

KvCache API ← High-level transformer attention interface │ ▼ TurboQuant ← Two-variant combiner: MSE (recommended) + Prod (unbiased) │ ├─── PolarQuant (Stage 1 — MSE-optimal) │ ├── Rotation (FWHT: randomised Hadamard) │ ├── Lloyd-Max scalar quantisation → centroids lookup │ └── Bitpack (2/3/4-bit packing + L2-norm scalar) │ └─── QJL (Stage 2 — 1-bit residual correction) ├── Quantized Johnson-Lindenstrauss transform └── 1-bit sign projection for unbiased inner products (Prod variant)

06 — Remaining Work

What Comes Next

The core library is production-complete. The roadmap items below extend capability and scale — none of them gate the candle-vllm integration, Prometheus Fabric deployment, or Prometheus Banking Mesh pilot.

Batch Processing API Next Priority

The current quantisation interface operates on single vectors. A quantize_batch API would allow the compression layer to process multiple KV vectors in one call — better cache utilisation and lower per-vector overhead at high throughput. This is the most impactful remaining API surface before considering GPU work.

GPU Decompression Kernels Roadmap

Current decompression runs on CPU. At large serving scale — many concurrent sessions, very long contexts — moving decompression on-device via CUDA or ROCm kernels eliminates the CPU round-trip entirely. Not required for any current deployment target; relevant when single-instance token throughput becomes the binding constraint.

C FFI Bindings Roadmap

Exposing the compression stack through a stable C ABI allows non-Rust runtimes and frameworks to consume TurboQuant compression without vendoring the Rust crate. Relevant once the library sees adoption outside the Prometheus ecosystem.

Allocation Regression Suite Roadmap

A benchmark harness with allocation tracking — verifying zero heap allocations per quantisation operation in the hot path — locks in the current performance characteristics permanently and prevents regression as the codebase evolves.

The library is production-optimised today. Zero external dependencies, zero unsafe blocks, SIMD-accelerated hot paths, full Result-based error handling across all public API surfaces, and 35 passing tests. The roadmap items above are capability extensions, not corrections.
